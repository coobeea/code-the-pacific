## 〇、这份文档是什么，怎么用

### 0.1 它解决什么问题

之前项目里的文档是**分散**的：评分依据在一份、资料在一份、计划在一份、技术选型在一份。每份都对，但**没有一份能把"我们要做什么"从上到下讲完**。

本文档的作用是把它们**串成一条线**：

```
          ┌──────────────────────────────────────────┐
          │   需求与目标说明书.md（本文档）★ 唯一源头   │
          │   要什么 → 为什么 → 做到什么程度 →        │
          │   用什么做 → 分几步做                     │
          └──────────────────────────────────────────┘
                 │            │            │
        ┌────────┘            │            └────────┐
        ▼                     ▼                     ▼
  评分规则与评审标准.md    技术选型.md      参赛计划与拿奖路线图.md
  （依据：为什么这么定）  （做法：技术细节）  （执行：任务与检查点）
        │                     │                     │
        └──────────────┬──────┴─────────────────────┘
                       ▼
              references/ 资料包（素材来源）
```

**冲突时以本文档为准。** 若其他文档与本文档不一致，改其他文档。

## 一、项目概述

### 1.1 一句话定义

> **做一个纯前端的 APEC 主题网页应用：在同一个项目里并列开发官方给出的四个选题方向，做成四个独立入口，用户（评委）从首页可以自由进入任一入口，比较同一套技术架构承载四种不同题材的成果。**

### 1.2 项目名称

| 项 | 内容 |
|---|---|
| 中文名 | 《码上亚太》APEC 2026 深圳峰会 AI 网页开发实训营 |

| GitHub 仓库 | `code-the-pacific` |

### 1.3 背景

- **赛事**：南山区第二十八届教育科技节 · AI 赛项，赛项主题《APEC 主题网页》实训营
- **国际背景**：APEC 第 33 次领导人非正式会议将于 **2026 年 11 月 18—19 日在深圳**举行，
  深圳是继上海、北京后第三座主办城市；主题「建设亚太共同体，促进共同繁荣」，优先领域「开放、创新、合作」

| 受众 | 他们关心什么 |

| **评委（第一受众）** | 评分表上的五个维度能不能一眼看出来；能不能打开；交的材料齐不齐 |

- **类型**：静态网站 / 单页应用（SPA），纯前端
- **规模**：1 个应用，4 个功能入口，约 12—16 个页面

### 3.1 ★ 核心需求 · 单项目四入口（本项目的立项特征）

#### R-01 · 四个选题方向全部开发

**需求描述**：官方给出的四个选题方向**不做取舍，全部开发**，并且放在**同一个项目（同一个仓库、同一个应用）**里，
以**四个独立入口**的形式并列存在。用户可从首页进入任一入口，在入口之间自由切换。

**为什么这样做**：

| 理由 | 说明 |
|---|---|
| 素材已齐备 | 四个方向的资料包已在 `docs/references/01~04` 准备完毕，边际成本低 |
| 架构可复用 | 四者共享同一套设计系统、数据层与页面骨架，做一个和做四个的差距远小于 4 倍 |
| 立意新颖 | "一套架构承载四种题材"本身就是原创性的体现，直接作用于「创意与原创性 20%」 |
| 素材新鲜 | 南山八景（2026-09 公布）等素材评委尚未见过 |
| 便于比较 | 四个方向并排呈现，可以直观比较不同题材的完成度与表现力 |

**形式约束**：

- 四个入口**同属一个应用**，不是四个独立仓库、不是四个独立站点
- 每个入口有**独立的路由命名空间**（如 `#/01-summit/...`）
- 首页是一个**展厅（Hub）**，承担"介绍项目 + 分发到四个入口"的职责
- 全局导航栏提供**入口切换器**，任何时候都能跳到其他入口

#### R-02 · 每个入口都是一个完整作品

**需求描述**：不能出现"某个入口只有一句话"的情况。每个入口最低完成标准：

1. **至少 1 个落地页**（该入口的首页，有完整视觉与信息层级）
2. **至少 1 个子页面**（详情/列表，可通过路由进入）
3. **至少 1 个可用交互**（筛选、切换、检索、展开、地图点位等任一）
4. **至少 1 处南山元素**（服务于「南山特色呈现 10%」，四个入口都要有）

#### R-03 · 统一的站点外壳与入口切换

**需求描述**：

- 全局顶栏：项目名 + 四个入口导航 + 当前入口高亮
- 全局底栏：资料来源出处、项目信息
- 首页展厅：四个入口的卡片式导览，各配一句话说明 + 特色截图
- 入口切换时状态干净（滚动复位、无残留动效）

#### R-04 · 公共层共享

**需求描述**：以下内容由四入口共用，**不得重复实现**：

| 公共层 | 内容 |
|---|---|
| 设计系统 | 配色（`@theme` 变量）、字体、间距、圆角、阴影、动效时长 |
| 布局组件 | `AppHeader` / `AppFooter` / `EntrySwitcher` / `PageShell` |
| 通用组件 | `SectionTitle` / `InfoCard` / `DataPanel` / `SourceList`（资料出处） |
| 数据层 | `apec.json`（峰会信息 + 21 经济体）、`nanshan.json`（南山数据）、`scenes.json`（八景） |
| 工具 | 图表封装、日期格式化、路由懒加载配置 |

> 💡 **这条需求是"四方向全做"能成立的关键。** 如果每个入口各写一套样式和组件，工作量是 4 倍，
> 21 天绝对做不完；共享公共层之后，每个新入口的**边际成本主要在"内容 + 1 个核心交互"**。

#### R-05 · 公网可访问（硬门槛）

**需求描述**：必须有真实可打开的网址，且满足：

- 手机 4G 网络可打开，首屏可交互时间 < 3 秒
- 部署自动化（push 即发布），部署记录本身作为「开发过程」证据
- 不得把源代码中的相对路径错误带上线（即不得出现白屏）

### 3.4 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| N-01 | 性能 | 首屏可交互 < 3s（4G）；**四个入口按路由懒加载**，避免首包过大 |
| N-02 | 体积 | 单入口 JS（gzip）尽量 < 300KB；图表库按需引入 |
| N-03 | 稳定性 | 全流程无控制台 error；任一交互连续点击不崩溃 |

| N-06 | 可维护性 | 内容与组件分离（内容在 JSON）；新增入口不改动公共层 |

| N-08 | 合规 | 不收集用户信息；素材来源合法；无抄袭 |
| N-09 | 可部署性 | 构建产物为纯静态文件；自动化部署可用 |

### 3.5 约束性需求：没有后台

**本项目是纯前端应用，没有服务器、没有数据库、没有 API、没有用户系统。**（详见第六章）

由此产生三条**必须遵守**的约束：

| 编号 | 约束 |
|---|---|
| X-01 | **不做任何需要"数据写到服务器"的功能**：不做登录注册、不做留言/评论/点赞落库 |
| X-02 | **不做在线信息收集**：E-04 的报名需求改为「展示页 + 跳转第三方表单（如腾讯问卷）」 |
| X-03 | **localStorage 只能用于"本机偏好"**：不得用来冒充"提交成功"（评委换设备就看不到） |

| **目标** | **三等奖** | 五维得分在有效作品中处于中上（约前 30%） | 主力目标 |
| **期望** | **二等奖** | 技术应用 30% + 交互完成度 20% 做满，四入口均有完整形态（约前 20%） | 努力方向 |
| **挑战** | **一等奖** | 在上一档基础上，有 1—2 个让人记住的原创交互，且"四方向并列"的立意被认可（约前 10%） | 争取 |

> **为什么把"有效作品"单列为底线**：获奖名额按**有效参赛作品**总数比例划定，
> 被判无效的作品**不进入评审基数**——也就是彻底出局。所以第一步不是"做得多好"，
> 而是"**别掉出有效范围**"。

### 4.3 成功标准（可验证）

项目完成时，以下每一条都必须为真：

- [ ] `https://coobeea.github.io/code-the-pacific/` 在手机 4G 下可打开，首屏 3 秒内可用
- [ ] 首页展厅可一次点击进入**四个入口中的任意一个**
- [ ] **四个入口**各自具备：落地页 + ≥1 子页 + ≥1 可用交互 + ≥1 处南山元素
- [ ] 全站浏览过程**无控制台报错**
- [ ] 手机 / 平板 / 桌面三种宽度下布局均正常
- [ ] 全站无编造内容；21 个成员经济体表述规范
- [ ] 三件套齐备，且过程文档覆盖官方点名的四个小节
- [ ] 页面上可追溯到主要资料的来源

### 4.4 明确"不做"的事（范围排除）

明确排除，是为了防止精力被稀释：

| 不做 | 原因 |
|---|---|
| 后台管理、用户登录、账号体系 | 没有后台（X-01） |
| 在线报名收集、留言评论、点赞投票落库 | 没有后台（X-02） |
| 依赖第三方实时接口的功能（实时汇率、实时天气等） | 稳定性优先；数据一律内置 |
| 服务端渲染、数据库、API 开发 | 纯静态交付 |
| 多语言切换（中英双语） | 收益低、工作量大；除非最后有余力 |
| 用户生成内容（UGC） | 没有后台，且涉及未成年人信息合规风险 |
| 把 21 个经济体/八景做到"百科级深度" | 以"可读、准确、好看"为界，不追求资料穷尽 |
| 重型动画特效、3D、视频背景 | 「交互**稳定**流畅」是评分项，收益低风险高 |
| 追求覆盖全部景点与全部议题 | 同上，宁少而精 |

### 4.5 优先级原则：纵深优先，横向其次

> **先把一个入口做成"完整的作品"，再把这个架构横向复制到其他三个入口。**

绝不"四个入口同时铺开、每个都做一半"。理由：

- 评审针对的是**一个作品**。四个半成品加起来不等于一个完整作品。
- 只要有一个入口是完整的，项目就随时处于"**可以提交**"的状态——这是 21 天里最重要的安全垫。
- 横向复制时，公共层已稳定、内容模式已跑通，速度会明显快于第一遍。

## 六、技术选型

> 完整版见 **`docs/技术选型.md`**（含版本号、配置代码、必踩的坑、降级方案）。本章为汇总。

### 6.1 一句话

> **纯前端、无后台：Vite 8 + Vue 3.5 + Vue Router 5（hash 模式）+ Tailwind CSS 4 + lucide 图标，
> 构建成静态文件后用 GitHub Actions 发布到 GitHub Pages。**

### 6.2 架构前提：没有后台

**这个项目没有服务器、没有数据库、没有 API、没有登录。**所有内容在 `npm run build` 时被"冻"进静态文件。

| 想做的事 | 没有后台的结果 | 我们的处理 |
|---|---|---|
| 用户登录注册 | ❌ 做不到 | 不做 |
| 留言/点赞/投票落库 | ❌ 做不到 | 不做，或降级 localStorage（仅本机） |
| **在线报名/问卷收集** | ❌ **收不到** | **跳转腾讯问卷等第三方表单**（X-02） |
| 后台改文案即时生效 | ❌ 做不到 | 改 JSON → 重新构建发布（几分钟） |
| 服务端渲染 / SEO | ❌ 没有服务端 | 静态 HTML 本就利于抓取；关键词写进 `<title>` / `<meta>` |

**无后台反而带来的好处**（都对得分有利）：

1. **稳定性** —— 没有服务器就没有宕机、接口超时 → 直接服务于「交互稳定流畅 20%」
2. **加载快** —— 静态文件走 CDN
3. **合规天然安全** —— 不收集任何用户信息 → 自动规避「未成年人信息需监护人同意」红线
4. **零成本、免备案** —— 静态托管免费，GitHub Pages 不涉 ICP 备案
5. **部署即留痕** —— 每次 push 就是一次发布记录，可直接作为"开发过程"证据

**localStorage 的边界**（易错点）：它只存在"打开页面的这台设备的这个浏览器"里，换设备/清缓存即丢。
判据：这份数据"**只有我自己看到就够吗**"？够 → 可用；需要"别人也能看到" → 做不到，改方案或不做。

### 6.3 技术栈

| 层 | 选型 | 版本 |
|---|---|---|
| 构建工具 | Vite | `8.3.2` |
| 框架 | Vue（Composition API + `<script setup>`） | `3.5.43` |
| 路由 | Vue Router（**hash 模式**） | `5.3.1` |
| 样式 | Tailwind CSS（CSS-first，`@theme` 定义设计令牌）+ `@tailwindcss/vite` | `4.3.3` |
| 图标 | lucide-vue-next（UI 图标）；八景图形标识**手绘 SVG** | `1.0.0` |
| 数据可视化 | **手写 SVG 优先**，复杂图用 ECharts + vue-echarts | `6.1.0` / `8.3.1` |
| 动画 | Vue 内置 `<Transition>` + `@vueuse/core` | `15.0.0` |
| 状态管理 | **不引入 Pinia**（数据全静态） | — |
| 部署 | GitHub Actions → GitHub Pages | — |

> 所有版本号均于 2026-10-04 用 `npm view` 实测，非记忆值。
> **Node 要求**：Vite 8 需要 Node `^20.19.0 || >=22.12.0`（本机 22.22.2 / 25.6.1 满足）。

### 6.4 三个必踩的坑（摘要）

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | `vite.config.js` 的 `base` 没设成 `'/code-the-pacific/'` | **线上白屏**（本地正常） | 配置写死仓库名，前后都有斜杠 |
| 2 | 路由用了 history 模式 | 刷新深链接 404 | 用 `createWebHashHistory()` |
| 3 | Pages 源设成「main 分支的 `/docs` 目录」 | 把文档目录当网站发布 | 源必须选 **「GitHub Actions」**，发布 `dist/` |

### 6.5 降级方案（进度告急时按顺序降，不推倒重来）

1. 砍掉 Vue Router → 单页多区块锚点跳转
2. Vue 降级为 CDN 引入 → 不需要 `npm run build`
3. 兜底回纯 HTML / CSS / JS

> **三档降级方案全部仍是"无后台"的**，第 3 档照样满足「在线部署、可在线访问」，照样能参赛。
> **真正会毁掉比赛的是一路硬扛、拖到最后没做完。**
>
> 对应到"四入口"目标：如果时间告急，**主动把入口数从 4 降到 1—2 个**，
> 也不算失败——因为架构上仍是同一个项目，减少的只是板块数量。
