## 一、拿奖的分数逻辑：钱要花在刀刃上

先算清楚：100 分里，哪些是"守"的，哪些是"攻"的。

| 分数类型 | 维度 | 权重 | 性质 |
|---|---|---|---|
| **保底分** | 主题契合 | 20% | 只要引用准确 + 紧扣 APEC，就能拿到 |
| | 南山特色呈现 | 10% | 只要放对元素，基本白送 |
| **决胜分** | 技术应用（AI 能力） | **30%** | 最大的单项，**且有一条硬性交付要求** |
| | 交互与页面完成度 | 20% | 评分措辞是「交互**稳定**流畅」 |
| **爆发分** | 创意与原创性 | 20% | 决定是三等奖还是一等奖 |

### 一句话战略

> **把 50% 的"完成度分"做满（技术应用 30% + 交互 20%），再用 1 个独特的原创交互去抢 20% 的创意分，剩下的 30% 靠规范引用自动到手。**

**为什么是这个顺序？**

- 技术应用 30% 里写死了「网页实现**互联网线上部署、可在线访问**」——没网址，这 30% 直接判不达标。这是**唯一的硬门槛**，必须最先解决。
- 交互 20% 看的是"稳定"，不是"炫"。做得越多越容易崩，**少而稳 > 多而卡**。
- 创意 20% 靠"不抄"。所以核心交互概念要**自己定**，不能等做到一半去参考站上找灵感——那时候已经晚了。

### 按获奖比例倒推

奖项按**有效参赛作品**总数的 10% / 20% / 30% 划定，即**前 60% 的有效作品都能获奖**。

推论：**只要成为"有效作品"，至少有三等奖。** 所以第一个战略目标不是"做得多好"，而是"别掉出有效范围"：

- ✅ 材料交齐（三样）
- ✅ 格式规范
- ✅ 紧扣主题
- ✅ 有公网网址

**先确保这三等奖，再往上打。** 这个顺序错了（比如先追炫酷功能、最后两天才补材料），风险极高。

## 二、核心决策（必须在阶段 1 之前拍板）

### 决策 1 · 选题方向：**四个方向全部开发**（单项目 · 四入口）

> ⚠️ **本条已被更新。** 原方案是"四选一"，现确立为**四个方向全部开发，置于同一项目内做成四个独立入口**。
> 完整需求见 **`docs/需求与目标说明书.md` 第 3.1 节（R-01）**。

四个方向的定位与开发顺序：

| 方向 | 素材现成度 | 南山特色 10% | 交互上限 | 定位 | 开发顺序 |
|---|---|---|---|---|---|
| 峰会资讯类 | 中（官方细节多待公布，有编造风险） | 弱 | 中 | 完整但更简 | 3rd |
| **城市名片类** | **高（南山八景现成）** | **满分潜力** | **高** | ★ **主推，先做成完整作品** | **1st** |
| 知识科普类 | 中（21 经济体数据要整理） | 弱 | 高 | 技术含量上限最高 | 2nd |
| 活动落地类 | 低（功能点最多） | 中 | 中 | 改为展示页 + 跳转第三方表单 | 4th |

**为什么可以四个全做**：四者共享同一套设计系统、数据层与外壳组件（见 R-04），
做一个和做四个的差距**远小于 4 倍**——每个新入口的边际成本主要是"内容 + 1 个核心交互"。

**为什么仍然先做城市名片类**：

1. **素材是现成的**：「南山八景」2026 年 9 月刚揭晓，八个名字 + 代表景点清单已确认，等于**页面骨架直接给好了**（见 `references/02-城市名片类-深圳南山.md`）。
2. **南山特色 10% 基本锁死**：整个入口就是讲南山的，这一项不可能丢。
3. **素材最新鲜**：八景名单是 2026 年 9 月才公布的，评委很可能还没见过别人用过。
4. **纵深优先的安全垫**：它一做完，项目就随时处于"可以提交"的状态（见 R-02、4.5）。

> ⚠️ **最大风险是精力分散**——四个半成品不等于一个完整作品。
> 应对：严守"先纵深、后横向"；时间告急时**主动把入口从 4 减到 1—2 个**，架构上仍是同一个项目，不算失败。

### 决策 2 · 原创交互概念：建议「八景一张图」

创意 20% 要抢，就必须有**一个让人记住的核心交互**。三个候选：

| 方案 | 核心交互 | 优势 | 风险 |
|---|---|---|---|
| **A · 八景一张图**（推荐） | 一张手绘风格的南山地图，八个景观点位可点击，点开侧栏展示详情 | 视觉冲击强、原创感足、天然扣南山 | 地图素材要自己画 |
| B · 八景时间轴 | 从 1700 年南头古城到今天前海观潮，横向时间轴串起八景 | 有叙事厚度、易体现"古今交融" | 时间跨度梳理要花功夫 |
| C · 八景数据图鉴 | 八景卡片墙 + 筛选（人文/生态/科创/生活）+ 数据面板 | 开发最快、最稳 | 原创感稍弱，容易撞车 |

**建议 A，但把 C 作为技术备份**：A 的地图如果做不出来，降级成 C 的卡片墙，交互框架不用重写。**这就是为什么不要在阶段 3 才发现方案做不出来。**

> ⚠️ 无论选哪个，**核心交互必须自己定**。参考站（见 `references/00-参考网站与素材来源清单.md`）只用来学信息层级和口径，形态要重新设计。

### 决策 3 · 技术方案：Vue 工程化开发 + GitHub Pages 静态部署

> **完整版见 `docs/技术选型.md`**（含版本号、配置代码、三个必踩的坑、降级方案）。

| 项 | 决策 | 理由 |
|---|---|---|
| 开发框架 | **Vue 3.5**（Composition API + `<script setup>`） | 八景这类"同类内容重复 8 次"的场景最适合组件化；且 AI 生成新写法的代码质量最高 |
| 构建工具 | **Vite 8** | 构建产物是纯静态文件，天然适配静态托管 |
| 路由 | **Vue Router 5 + hash 模式** | GitHub Pages 无服务端重写，hash 模式零风险（稳定性 > 网址好看） |
| 样式 | **Tailwind CSS 4**（CSS-first） | 不用切文件写 CSS，改动即时，配合 AI 效率最高 |
| 图标 | **lucide-vue-next** 为主 | 零配置、按需打包；八景图形标识建议手绘 SVG |
| 数据可视化 | **手写 SVG 优先**，复杂图用 ECharts | 手写 SVG 在过程文档里更能体现技术理解 |
| 动画 | **Vue 内置 `<Transition>`** + `@vueuse/core` | 「交互稳定流畅」是评分项，不引重型动画库 |
| 状态管理 | **不引入 Pinia** | 数据全静态，多一个依赖多一个坑；"不引入"写进过程文档反而加分 |
| 部署 | **GitHub Actions → GitHub Pages** | 仓库已建好，push 即自动发布，部署记录本身就是开发过程证据 |

**架构前提 · 纯前端、没有后台**（详见 `docs/技术选型.md` 第二节）：

- **没有服务器、没有数据库、没有 API、没有登录**。所有内容在 `npm run build` 时"冻"进静态文件。
- 数据放 `src/data/*.json`，检索/筛选全在前端内存里做——数据量几百条以内毫无压力。
- **做不到的事要提前知道**：收不到表单（报名/问卷要改用腾讯问卷等第三方表单）、点赞投票落不了库、改文案要重新构建发布。
- **localStorage 只在本机**，不能冒充"数据提交"——需要"别人也能看到"的数据，一律不用它。
- **对选题的直接影响**：01/02/03 三个方向与纯静态天然兼容；**04 活动落地类若要做"在线报名收集名单"，无后台做不到**，须改为「展示页 + 跳转腾讯问卷」。这是再次支持选 02 城市名片类的架构层面理由。
- **反过来是好事**：没有服务器＝没有宕机与接口超时（对应「交互稳定流畅」）；静态托管免备案、免费用；**一个用户信息都不收集**，天然规避「未成年人信息需监护人同意」这条合规红线。

**交付形态澄清**：用 Vue 开发 ≠ 交付 Vue 源码。`npm run build` 产出的 `dist/` 里就是纯 HTML/CSS/JS，**符合"网页化交付 + 线上可访问"的要求**。

**部署上线后预计地址**：`https://coobeea.github.io/code-the-pacific/`

**三个必踩的坑（写在技术选型文档里，此处只列结论）**：

1. `vite.config.js` 的 `base` 必须设为 `/code-the-pacific/`，否则线上**白屏**
2. 路由必须用 `createWebHashHistory()`，否则刷新深链接 **404**
3. Pages 源**不能**选「main 分支的 /docs 目录」——那个目录被我们用来放项目文档了；要选「GitHub Actions」

> 💡 **部署这件事要在阶段 1 就做完**，哪怕那时候页面只有一句话。因为这是 30% 的硬门槛，早通早安心。**先让它能用网址打开，再往里填内容。**
>
> ⚠️ 与之配套的风险：Vue 工程化对四至八年级学生有难度。**阶段 1 的检查点就是这条工具链能不能跑通**；跑不通就按技术选型文档里的「最小可行路径」逐级降级，**不要推倒重来**。

## 六、风险与预案

| 风险 | 影响 | 预案 |
|---|---|---|
| **时间不够** | 最高风险。10 月可能有期中考试等冲突 | 阶段 1 就上线骨架；任选阶段超时 2 天，直接砍功能保材料 |
| **核心交互做不出来** | 创意分受损 + 拖垮进度 | 提前准备降级方案（方案 A → 方案 C 卡片墙），交互框架不重写 |
| **GitHub Pages 访问慢/被墙** | 评委打不开 = 30% 归零 | 备选 Cloudflare Pages / Vercel，同一套静态文件直接换部署 |
| **素材版权问题** | 可能被取消资格 | 会标、标识类素材一律自绘，不直接使用官方原图 |
| **过程文档写不出来** | 材料不全，丢资格 | 阶段 3 开始**边做边记**，不留到最后回忆 |
| **最后一天才发现网址挂了** | 灾难性 | 阶段 5 的第一件事就是**换设备验证网址**；10/25 是纯缓冲日 |

## 七、每天的最小节奏（避免拖延）

学生每天有效投入 **1.5 - 2 小时** 即可完成本计划：

| 时段 | 内容 |
|---|---|
| 前 10 分钟 | 打开昨天的成果，确认线上版本正常 |
| 中间 60-90 分钟 | 按当天任务推进，用 AI 工具辅助编码 |
| 后 10 分钟 | **提交到 GitHub 一条 commit + 在过程文档记一行今天做了什么** |

> 最后这 10 分钟是关键。它同时解决三件事：① 过程文档不用最后回忆；② 仓库提交记录成为开发过程证据；③ 每天都有可见进度，不容易中途放弃。
