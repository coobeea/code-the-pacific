## 一、先把三个前提说清楚

这三个前提决定了整条技术路线能不能成立，其中**第三个（没有后端）是架构的起点**，单独成节（见第二节）。

### 前提 1 ·「交付 HTML」指的是**构建产物**，不是源码

原始需求里写着「网页实现互联网线上部署、可在线访问」，所以最终交付物必须是**能直接在浏览器打开的静态文件**。

用 Vue 开发 **不违背** 这个要求。因为：

```
你写的代码（.vue 文件）
        │
        ▼  npm run build   ← 构建这一步是关键
        │
dist/ 目录
├── index.html        ← 纯 HTML
├── assets/*.js       ← 纯 JavaScript
└── assets/*.css      ← 纯 CSS
```

**`dist/` 里出来的就是你要的 HTML/CSS/JS，没有任何 Vue 运行时依赖需要评委去装。** 浏览器打开 `index.html` 就能跑。

所以「用 Vue 开发」和「最终交付 HTML」这两件事**不冲突**。真正交付的性质由构建产物决定，不由开发方式决定。

### 前提 2 · 赛事不限制开发方式，但限制**结果形态**

原文只说了要「可在线访问」，**没有**限制用什么写。所以 Vue + Tailwind 完全合规。

**唯一的硬约束**：构建产物必须是能跑在静态托管上的文件。这套选型满足——不需要 Node 服务器、不需要数据库、不需要后端。

### 前提 3 · **没有后台，整个作品是纯前端应用**

这一点你说得对，而且它比看起来更重要。

**「没有后台」不是一个遗憾，它就是这个项目的架构起点。** 这套技术选型里有一半的取舍，都是在为这个前提服务。

详细展开见下一节——包括它让你**做不到**哪些事、哪些事必须换方案、以及它对选题方向的直接影响。

## 二、系统架构：纯前端应用，没有后台

### 2.1 架构长什么样

```
普通网站（有后台）
┌────────┐   HTTP    ┌─────────────┐   SQL    ┌──────────┐
│ 浏览器 │ ────────▶ │  服务器进程  │ ───────▶ │  数据库   │
└────────┘           └─────────────┘          └──────────┘

我们的作品（纯前端 / 无后台）
┌────────┐    读取     ┌─────────────────────────────┐
│ 浏览器 │ ─────────▶ │ GitHub Pages（一堆静态文件） │
└────────┘            └─────────────────────────────┘
     ▲
     └── 页面内容、数据、路由、筛选、图表
         全在浏览器里跑完，没有任何请求发给「后端」
```

具体说，这个项目里**不存在**这些东西：

- **没有服务器进程** —— 没有任何一段服务端代码在跑着等请求
- **没有数据库** —— 没有 MySQL / MongoDB / Supabase，一条 SQL 都没有
- **没有 API 接口** —— 没有一个 `/api/xxx` 是活的，不存在 `fetch` 后端
- **没有用户系统** —— 没有登录、注册、token、会话
- **没有后台管理界面** —— 没有"登录后台改内容"这回事

**所有内容都在 `npm run build` 那一刻被"冻"进静态文件里。** 上线之后，页面上的每一个字、每一张图、每一组数据，都已经是一个文件的一部分了。

### 2.2 没有后台，哪些事就**做不到**

这张表要看，因为它直接决定选题方向能不能做。

| 想做的事 | 没有后台的结果 | 我们的处理 |
|---|---|---|
| 用户注册 / 登录 | ❌ 完全做不到 | 不做。作品是展示型，不需要账号体系 |
| 数据存到服务器（留言、评论、点赞落库、投票计数） | ❌ 做不到 | 不做，或降级为 localStorage（见 2.5） |
| 在线收集报名信息 / 问卷回收 | ❌ 收不到，也存不了 | **改用腾讯问卷等第三方表单**，生成外链或二维码，本站只负责展示与跳转 |
| 后台改文案、前台立即生效 | ❌ 做不到 | 改 JSON → 重新构建 → 自动发布（赛期内完全够用，一次几分钟） |
| 服务端渲染 / SEO 抓取 | ❌ 没有服务端 | 静态 HTML 本身就利于抓取；APEC 关键词写进 `index.html` 的 `<title>` 与 `<meta>` |
| 权限控制、支付、消息推送 | ❌ 不需要 | 与赛事无关 |

### 2.3 没有后台反过来带来的**五个好处**（都对得分有利）

1. **稳定性 —— 直接对应「交互稳定流畅 20%」**
   没有服务器，就没有"服务器挂了""接口超时""数据库连不上"。静态文件的故障面小得多。
2. **加载快**
   静态文件走 CDN，首屏基本是"能多快有多快"，不会卡在等接口。
3. **合规上天然安全**
   评分文档里有一条合规红线：「涉及未成年人信息需监护人同意」。
   **我们一个用户信息都不收集**，这条红线自动规避——这不是侥幸，是架构决定的结果。
4. **零成本、无需备案**
   静态托管免费；托管在 GitHub Pages，不涉及国内服务器的 ICP 备案问题。
5. **部署即留痕**
   `git push` 一次就是发布一次。这些提交记录本身就是「开发过程」的天然证据，可以直接写进过程文档。

### 2.4 那"数据"放哪？—— 静态数据方案

没有数据库，数据就放在代码里。这是标准做法，不是权宜之计。

| 原本"该数据库做"的事 | 我们的替代方案 |
|---|---|
| 存八景 / 南山 / APEC 内容 | `src/data/scenes.json`、`nanshan.json`、`apec.json`，构建时打包进 JS |
| 检索 / 筛选 / 排序 / 分类切换 | **纯前端内存计算**（`filter` / `computed`）。数据量几百条以内，没有任何性能问题 |
| 图表数据 | 同上，直接喂给 ECharts 或手写 SVG |
| 图片 / 音视频 | 预处理好放进 `public/`，构建时原样复制。**不要在浏览器里做图片处理** |

> 💡 **为什么这样反而更好**：内容全在 JSON 里，改文案不用碰 `.vue` 组件，八个景点也不用写八遍模板。既省时间，也是过程文档里「数据与视图分离」的实证。

### 2.5 ⚠️ localStorage 的边界（这里最容易搞错）

纯前端唯一能"存东西"的地方是浏览器本地的 `localStorage` / `sessionStorage`。它是**可以用的**，但有一个必须清楚的边界：

> **localStorage 只存在"打开页面的这台设备的这个浏览器"里。**
> 换一台电脑、换一个浏览器、清一次缓存 → 数据全没了。
> 它**不是**服务器存储，**绝对不能**用来冒充"数据提交"。

| ✅ 可以（正当用途） | ❌ 不可以（会出问题） |
|---|---|
| 记住"我上次看的景点" | 把报名信息存 localStorage 当"已提交" |
| 收藏的八景 | 把点赞数 / 投票数存 localStorage 当"总票数" |
| 深浅色主题偏好 | 期待评委在别的设备上看到你存的内容 |

**判据很简单**：这份数据"只有我自己看到"就够吗？
- 够 → 可以用 localStorage
- 需要"别人也能看到" → 没有后台就是做不到，**要么换第三方表单，要么这项功能不做**

### 2.6 这个前提如何影响**选题方向**（重要）

| 选题方向 | 与「无后台」的冲突 | 结论 |
|---|---|---|
| 01 峰会资讯类 | 无冲突，纯展示内容 | ✅ 可做 |
| **02 城市名片类** | **无冲突**：八景 + 数据 + 地图全是静态内容 | ✅ **最匹配** |
| 03 知识科普类 | 无冲突：检索 / 筛选走前端内存足够 | ✅ 可做 |
| 04 活动落地类 | ⚠️ 若做成"在线报名并收集名单"，**做不到** | 需改为「展示型落地页 + 跳转腾讯问卷」 |

> 这也是**从架构角度又一次支持推荐「02 城市名片类」**：它天然就是纯静态的形态，一点也不用为了迁就架构而砍功能。
> 而 04 方向如果一开始没意识到这点，做到一半才发现"报名填了收不到"，返工代价会很大。

### 2.7 倒过来看：技术栈里哪些是为「没有后台」服务的

| 选型 | 它在"无后台"里的角色 |
|---|---|
| **Vite 构建** | 把 Vue 源码编译成静态文件——这一步是"没有服务器也能跑"的关键 |
| **GitHub Pages** | 纯静态托管，本来就只服务静态文件，与我们的形态天然咬合 |
| **JSON 数据文件** | 站在"数据库"的位置上 |
| **Vue Router 用 hash 模式** | 正因为**没有服务端可以做路由重写**，才必须用 hash（见第四节第 3 条） |
| **不装 Pinia** | 没有服务端状态、没有跨会话数据要管，状态管理库没有用武之地 |
| **ECharts / 手写 SVG** | 图表在客户端渲染，数据是构建时打包进去的，不请求任何接口 |

一句话：**这套技术栈不是"顺便没有后端"，而是专门为"没有后端"挑的。**

## 四、逐项选型理由

### 1. 构建工具：Vite 8

**推荐**：`vite@8.3.2`

- Vue 官方脚手架默认就是它，生态最顺
- 开发时 `npm run dev` 改完代码浏览器立刻更新，21 天的时间紧张，这个反馈速度很关键
- 生产构建产物是纯静态文件，**天然适配 GitHub Pages**（也是我们"无后台"能成立的关键一步）

**为什么不用 Nuxt？** Nuxt 是服务端渲染框架，要跑 Node 服务器。我们的托管环境（GitHub Pages）是纯静态，用不上，反而增加复杂度。**这个项目不需要 SSR。**

**备选**：如果只是想最快跑起来，`npm create vue@latest` 官方脚手架会问你要不要 Router，勾上即可，比手写配置省事。

---

### 2. 框架：Vue 3.5（Composition API + `<script setup>`）

**推荐**：`vue@3.5.43`

**为什么锁 3.5 而不是上 3.6？**

现在（2026-10-04）npm 上的最新**稳定版是 3.5.43**。3.6.0 还在 RC（候选发布）阶段，RC 版本不要用——比赛项目不承担这种风险。

**写法上只用 `<script setup>`**：

```vue
<script setup>
import { ref, computed } from 'vue'
const scenes = ref([...])
const active = ref(null)
</script>

<template>
  <div v-for="s in scenes" :key="s.id" @click="active = s">
    {{ s.name }}
  </div>
</template>
```

理由：这是现在 Vue 的官方主流写法，**AI 工具生成这种代码的质量明显高于老式 Options API**（训练语料里新写法更主流），对我们靠 AI 辅助编码的路线来说，这一点比"好不好学"更重要。

---

### 3. 路由：Vue Router 5 —— ⚠️ **必须用 hash 模式**

**推荐**：`vue-router@5.3.1`

这是整套选型里**最容易踩坑的一处**，单独讲。它的根源正是「没有后端」。

**问题**：GitHub Pages 是**纯静态托管，没有服务端路由重写**。也就是说，如果用户直接在地址栏输入或刷新 `https://coobeea.github.io/code-the-pacific/scene/nanshan`，服务器找不到这个物理路径，会返回 **404**。

**两种解法对比**：

| 方案 | 写法 | 网址长这样 | 风险 |
|---|---|---|---|
| **hash 模式**（推荐） | `createWebHashHistory()` | `.../#/scene/nanshan` | **零风险**，纯前端锚点，任何静态托管都支持 |
| history 模式 | `createWebHistory()` | `.../scene/nanshan` | 需要额外把 `index.html` 复制成 `404.html` 当兜底，多一个构建步骤 |

**结论**：**用 hash 模式**。理由是评分里写着「交互**稳定**流畅」，稳定性比网址好看重要得多。多一个 `#` 不影响任何得分项。

```js
// src/router/index.js
import { createRouter, createWebHashHistory } from 'vue-router'
import HomeView from '../views/HomeView.vue'
import SceneDetailView from '../views/SceneDetailView.vue'
import ApecView from '../views/ApecView.vue'

const router = createRouter({
  history: createWebHashHistory(),
  routes: [
    { path: '/', name: 'home', component: HomeView },
    { path: '/scene/:id', name: 'scene', component: SceneDetailView },
    { path: '/apec', name: 'apec', component: ApecView },
  ],
  scrollBehavior: () => ({ top: 0 }),
})

export default router
```

> 📌 `scrollBehavior: () => ({ top: 0 })` 这一行别漏。否则从八景详情返回首页时，页面会停在滚动中间的位置——**这是评委最容易感知到的"不流畅"**。

### 4. 样式：Tailwind CSS 4（CSS-first）

**推荐**：`tailwindcss@4.3.3` + `@tailwindcss/vite@4.3.3`

**Tailwind 对我们的真正价值**：不用在 HTML 和 CSS 文件之间来回切换。八景卡片要调间距、颜色、圆角，直接在标签上写 `p-6 rounded-xl bg-white`，**改动是即时的、局部的**。这对"21 天要出成品"和"AI 生成代码"两个场景都是效率最大化。

**v4 的配置方式变了**（和网上大部分老教程不一样，注意别照着旧教程做）：

| 项 | v3 老写法（❌ 不要用） | v4 新写法（✅ 用这个） |
|---|---|---|
| 引入 | `@tailwind base; @tailwind components; @tailwind utilities;` | `@import "tailwindcss";` |
| 配置文件 | 需要 `tailwind.config.js` | **不需要**，配置写在 CSS 里 |
| PostCSS | 需要 `postcss.config.js` | **不需要**，Vite 插件内置了 |
| 内容扫描 | 需要手写 `content: [...]` | **自动检测** |

```js
// vite.config.js
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  base: '/code-the-pacific/',   // ⚠️ 见第六节坑 1
  plugins: [vue(), tailwindcss()],
})
```

```css
/* src/style.css */
@import "tailwindcss";

@theme {
  --color-sea-800: #0C447C;
  --color-sea-600: #185FA5;
  --color-tech-600: #1D9E75;
  --font-sans: "PingFang SC", "Noto Sans SC", system-ui, sans-serif;
}
```

> `@theme` 里定义的每个色值会**同时**生成工具类（`bg-sea-800`）和 CSS 变量（`var(--color-sea-800)`），两边都能用。
> 具体配色在阶段 1 定，建议方向：**海洋蓝（APEC 议题的开放感）+ 科创青（南山气质）+ 一点暖橙点缀**。

**⚠️ 浏览器兼容提示**：Tailwind v4 依赖较新的 CSS 特性（`@property`、`color-mix()`），官方目标大致是 **Safari 16.4+ / Chrome 111+ / Firefox 128+**。这三个版本都是 2023 年的，2026 年的设备基本都满足。

但有一个真实场景要考虑：**评委可能在微信内置浏览器里打开链接**。如果对方是较老的安卓微信，可能出现样式异常。这个概率不高（低概率风险），应对办法写在第八节。

**备选**：如果实测发现兼容问题且改不动，降到 `tailwindcss@3.4.x`——v3 浏览器支持面更广，代价是需要写 `tailwind.config.js` 和 `@tailwind` 三个指令（回到老写法）。

### 5. 图标：lucide-vue-next 为主，Iconify 为备

**推荐**：`lucide-vue-next@1.0.0`

```vue
<script setup>
import { MapPin, ArrowRight, Search } from 'lucide-vue-next'
</script>

<template>
  <button>
    <MapPin :size="16" />
    <span>八景地图</span>
    <ArrowRight :size="16" />
  </button>
</template>
```

**为什么选它**：

- **零配置**：装完直接 `import { 图标名 }` 当组件用，不需要任何插件或配置
- **按需打包**：只打包你真正用到的图标，不会因为图标库大而拖慢加载
- **风格统一**：线条风格，用在导航、按钮、状态提示上很干净

**它的局限**：图标是西方线条风格，**缺少中国传统文化题材**（比如牌坊、古塔、岭南建筑这类）。如果你想给"南山八景"配中国风的图标，它给不了。

**这种情况上 Iconify**：`@iconify/vue@5.0.3` + 按需安装图标集：

```bash
npm i -D unplugin-icons @iconify-json/mdi
```

Iconify 汇集了 150+ 个图标库、20 万+ 图标，可以**编译时内联**（不需要运行时联网拉图标，也就不存在"加载慢"和"图标裂了"的问题）。

**我的建议**：**先用 lucide 把 UI 图标做完**（导航、按钮这类），八景的图形标识**建议直接用 SVG 手绘**——一张手绘风的南山轮廓图比任何现成图标库都更能拿「创意与原创性」的分。别为了配图标把时间耗在找图标库上。

### 6. 数据可视化：ECharts 6 + vue-echarts

**推荐**：`echarts@6.1.0` + `vue-echarts@8.3.1`

南山数据板块（GDP 破万亿、上市公司 218 家、国高企 6037 家、每万人发明专利 860 件）需要图表来撑「技术应用（AI 能力）30%」里的"表现力"。

**为什么选 ECharts 而不是 Chart.js**：

| | ECharts 6 | Chart.js 4.5.1 |
|---|---|---|
| 中文文档 | 完善 | 一般 |
| 图表类型 | 非常丰富（关系图、地图、雷达） | 基础类型为主 |
| 打包体积 | 较大（可**按需引入**减小） | 更小 |
| 适合场景 | 数据面板、多图联动 | 单张简单图表 |

**关键做法——按需引入**，否则打包体积会很难看：

```js
// 只引你真正用到的图表类型和组件
import { use } from 'echarts/core'
import { BarChart } from 'echarts/charts'
import { GridComponent, TooltipComponent } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'
use([BarChart, GridComponent, TooltipComponent, CanvasRenderer])
```

> 📌 ECharts 在"无后台"项目里的定位是**纯客户端渲染**——数据是构建时打包进去的，不请求任何接口。体积控制因此更重要。

**如果只画 2-3 张简单柱状图**：直接用 Chart.js 更省事，或者干脆**手写 SVG**——`<rect>` 画柱子、`<circle>` 画点，零依赖，而且"纯手写 SVG 图表"在过程文档里比"装了个图表库"更能体现对技术的理解。**这是我对这一项的真实建议：手写 SVG 优先，ECharts 用于确实画不出来的复杂图。**

### 7. 动画：**不引重型动画库**

**推荐**：Vue 内置 `<Transition>` / `<TransitionGroup>` + `@vueuse/core@15.0.0`

这一项和前面的"越强大越好"取向相反，理由很直接：

> **评分原文是「交互稳定流畅」。**

动画库（GSAP 3.15.0 / motion-v 2.5.2）确实更强，但每一个都意味着更多的初始化时序、更多的浏览器兼容层、更多的"某台设备上不动了"的可能性。**在 21 天的项目里，动画是收益最低、风险最高的一环。**

**具体做法**：

```vue
<script setup>
import { useIntersectionObserver } from '@vueuse/core'
const target = ref(null)
const visible = ref(false)
useIntersectionObserver(target, ([{ isIntersecting }]) => {
  if (isIntersecting) visible.value = true
})
</script>

<template>
  <div ref="target" :class="visible ? 'opacity-100' : 'opacity-0 translate-y-2'"
       class="transition-all duration-500">
    滚动到视口内再淡入
  </div>
</template>
```

CSS `transition` + `@vueuse/core` 的 `useIntersectionObserver`，能实现"滚动淡入""切换过渡"这类**看起来足够高级**的效果，而且：

- 浏览器原生渲染，**不会卡**（动效走进合成层）
- 出问题容易定位
- 写进过程文档是个很好的技术细节

### 8. 状态管理：**不装 Pinia**

**决策：不引入。**

`pinia@4.0.3` 是好东西，但这个项目不需要：

- 数据是**静态的**（八景、南山数据、APEC 信息），写死在 `src/data/*.json` 里
- 没有跨页面的动态状态共享需求
- **没有登录、没有用户会话、没有需要在多端同步的数据**（因为没有后端）

**引入 Pinia 的唯一结果是多一层概念、多一个可能出错的地方。** 用 `ref` + `provide/inject` 应付不了再上，但按这个项目的形态，基本不会用到。

> 少一个依赖，就少一个 `npm install` 失败的可能，少一份过程文档要解释的东西。**在时间紧张的项目里，"不引入"是一个值得主动做出的技术决策**，写进过程文档反而是加分项。

### 9. 3D / Three.js：作为「可选增强层」的取舍（2026-10-04 记录 · 负责人应创作者要求补记）

**结论先行**：不整体否定 3D，但把它定位成**可选增强层**——主链路不依赖，最多用在 1 处 hero。技术 30% 考的是「熟练度与完成度」，不是「有没有 3D」；而「交互稳定流畅 20%」才是 3D 最容易反噬的分。因此优先级是：**先把稳定 + 部署 + 内容做满，有余力再加一处三点增强**。Three.js 版本装时以 `npm view three version` 实测为准，不写记忆值。

**四条硬约束（违反即不做）**：
1. **只用在一处**：建议 E-02 名片首屏「鲲鹏 / 粒子地球 / 南山地形」或首页展厅的一个视觉焦点；其余页面保持 2.5D（SVG 视差、CSS 3D transform、层叠阴影），立体感多半靠"分层 + 视差 + 光影"，不一定真上 WebGL。
2. **懒加载 + 隔离**：`import('three')` 动态加载、只在进入该 hero 时挂载；three（min ~600KB+）必须**按需引入 + 单独 chunk**，绝不进首屏主包。
3. **自动降级**：WebGL 不可用 / 低端设备 / 显存或上下文丢失 / `prefers-reduced-motion` → 回退到静态 SVG 或 CSS 动画；主链路对 three **零依赖**，去掉 3D 页面照常能用。
4. **实测**：手机、微信内置浏览器、老显卡都点一遍不掉帧、不黑屏（直接对应「稳定流畅 20%」）。

**关于「商业化 / 付费 3D 组件」的合规提醒（对应红线：原创 + 版权）**：
- Spline、Rive、付费 Three.js 组件包等，导出资源常带**许可限制**；用前确认是否允许商用/参赛、是否要求署名。
- 纯前端无后台下，外部 3D 模型/贴图必须**下载打进 `public/` 本地托管**，不能运行时联网拉（否则评委环境拉不到 = 白屏，且违反"不依赖第三方"）。
- 守「必须原创」：3D 场景的构图/元素要自己做，**不要整包套用现成模板**——抄袭/侵权一经查实取消资格。

**推荐落地顺序**：先用 0 依赖的 **CSS 3D transform + SVG 视差分层**把"立体感"做出来（性价比最高、最稳）；确有额外余力且实测通过，再评估上 Three.js 单点 hero。

## 六、⚠️ 三个必须提前知道的坑

### 坑 1 · `base` 没配 → GitHub Pages 上**白屏**

GitHub Pages 的项目站点地址是 `https://<用户名>.github.io/<仓库名>/`，比根路径多了一层。

Vite 默认按根路径 `/` 生成资源引用，结果就是 `https://coobeea.github.io/assets/index.js` —— 404，页面白屏。

**解决**：`vite.config.js` 里必须写死仓库名：

```js
export default defineConfig({
  base: '/code-the-pacific/',   // ← 前后都有斜杠，必须和仓库名完全一致
  plugins: [vue(), tailwindcss()],
})
```

**这个坑的特征是"本地一切正常，一上线就白屏"**，很容易在阶段 1 部署时卡住。所以写在最前面。

### 坑 2 · SPA 深链接刷新 404 → 已用 hash 模式规避

见第四节第 3 条。用 `createWebHashHistory()` 就不存在这个问题。**根源就是没有服务端路由重写。**

### 坑 3 · **不要**把 Pages 源设成「main 分支的 /docs 目录」

GitHub Pages 有个选项是「Deploy from a branch → 分支选 main → 文件夹选 `/docs`」。

**千万别选这个。** 因为我们的 `docs/` 目录**已经被用来放项目文档了**（规则文件、计划、资料包），里面是 Markdown，不是网页。一旦选它，Pages 会把文档目录当网站发布，得到的是一堆 Markdown 原始文本，而不是作品。

**正确做法**：Pages 源选 **「GitHub Actions」**，由构建流程把 `dist/` 发布出去（见下一节）。

## 七、开发与部署

### 本地开发

```bash
cd /Users/liyufeifei/git/code-the-pacific

# 安装依赖（用 vite 8，需要 Node >= 20.19）
npm install

# 启动开发服务器，默认 http://localhost:5173/
npm run dev

# 构建生产版本，产物在 dist/
npm run build

# 本地预览构建产物（重要：验证 base 路径是否正确）
npm run preview
```

> `npm run preview` 这一步别跳过。它跑的是真实构建产物，能提前发现只有上线才会暴露的问题。

### 自动部署：GitHub Actions

**`.github/workflows/deploy.yml`**：

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

**一次性设置**：仓库 → Settings → Pages → Source 选 **「GitHub Actions」**。

**之后的流程**：往 `main` 分支 push 一次，Actions 自动构建并发布。预计网址：

> `https://coobeea.github.io/code-the-pacific/`

**`.gitignore`**：

```
node_modules/
dist/
.DS_Store
*.local
```

> `dist/` 要忽略——它由 Actions 自动构建，不需要进仓库。（`docs/` 要提交，它是过程材料。）

## 八、这套选型的风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **GitHub Actions 构建失败** | 中 | 网址更新不了 | 保留 `npm run build && npx gh-pages -d dist` 手动发布作为备选路径 |
| **Tailwind v4 在旧浏览器渲染异常**（如老版微信内置浏览器） | 低 | 评委看到的样式错乱 | ① 阶段 1 就用手机微信打开实测；② 出问题降级到 `tailwindcss@3.4.x`；③ 页面顶部加一行"建议使用最新版浏览器"提示 |
| **GitHub Pages 国内访问慢** | 中 | 评委打不开 | 同一套 `dist/` 可直接部署到 Cloudflare Pages / Vercel，改托管不改代码 |
| **ECharts 打包体积过大** | 中 | 加载慢，显得"不流畅" | 按需引入；或改手写 SVG 图表 |
| **误把 localStorage 当"提交"** | 中 | 报名/投票数据丢失，功能等同失效 | 严守 2.5 节的判据：需要"别人也能看到"的数据一律不用 localStorage |
| **21 天内学不完 Vue** | 中 | 进度崩 | 见下方"最小可行路径" |
| **引入 Three.js 3D 拖垮稳定 / 体积** | 中 | 卡顿、首屏变慢，反扣"稳定流畅 20%" | 只在 1 处 hero 用；按需 import + 懒加载单独 chunk；WebGL 不可用/低端设备/减少动态自动降级为 SVG/CSS；先保稳定再谈 3D |

### 最小可行路径（进度告急时的降级方案）

如果到阶段 1 结束时发现 Vue 学起来吃力，**按顺序降级，别推倒重来**：

1. **砍掉 Vue Router**：改成单页多区块（锚点跳转），`<section id="scenes">`
2. **再把 Vue 降级为非构建用法**：改用 CDN 引入 Vue，HTML 里直接写模板，不需要 `npm run build`
3. **最后兜底**：纯 HTML/CSS/JS，手动复制部署

**降级不等于失败**——第 3 档照样满足「在线部署、可在线访问」，照样能参赛。**真正会毁掉比赛的是一路硬扛、拖到最后没做完。**

> 值得强调：**三档降级方案全部都是"无后台"的**。第 3 档纯 HTML/CSS/JS 甚至是最彻底的纯前端——所以"没有后端"这个前提不会因为降级而失效。

### 难度提示

坦白说：**Vue + Vite + Tailwind 这套工程化组合，对一个四到八年级的学生来说是有难度的**（光"装依赖—跑 dev server—构建—部署"这条链路就有不少新概念）。

- 如果是**学生本人**主导开发：建议先花半天时间确认能跑通一个"Hello World + Tailwind 生效"的最小项目，能跑通再往下做。跑不通就走上面的最小可行路径。
- 如果是**老师或家长**主导开发：这套选型很合适，AI 辅助编码的产出在 Vue + Tailwind 语境下质量最高。

无论哪种情况，**阶段 1 的检查点（10/07 拿到公网网址）都是最硬的验证**——它验证的不是"代码写完了"，而是"整条工具链通了"。

## 十、顺带解决一件事：过程文档的「AI 辅助编码说明」怎么写

主题三的技术应用占 30%，过程文档里点名要写「**AI 辅助编码使用说明**」。这套技术选型天然给了你充足的素材，可以这样组织：

| 小节 | 素材来源 |
|---|---|
| 用了哪些 AI 工具 | 腾讯元宝 / WorkBuddy / CodeBuddy（赛项指定工具） |
| 分几类任务用 AI | ① 生成组件骨架（`SceneCard.vue`）② 写 Tailwind 类名 ③ 调试构建报错 ④ 生成 JSON 数据格式 |
| AI 生成后我改了什么 | 例如"AI 生成的卡片在手机上溢出了，我改成 `grid-cols-1 md:grid-cols-3`"——**这类具体细节比泛泛而谈的"用 AI 提高了效率"有说服力得多** |
| AI 帮不上、靠自己的部分 | 例如"八景地图的点位坐标是我照着南山地图自己标的""配色方案是我参考会标定的" |

> 💡 **越具体越加分。** 写"用 AI 生成页面"是空话；写"AI 第一次生成的图表把单位写成美元，我改成人民币并重排了刻度标签"——这才叫"熟练度"。

**顺带一个加分点**：可以专门写一段「**为什么我们没有做后台**」——说明这是**主动的架构决策**（纯静态托管 → 稳定性更高、加载更快、不收集未成年人信息因而更合规），而不是能力不足。这段话同时呼应「技术应用 30%」和「交互稳定流畅 20%」，是很划算的一段。
